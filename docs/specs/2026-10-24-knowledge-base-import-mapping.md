# 知識庫匯入對照規格

日期：2026-10-24
狀態：草稿（issue #62，母規格 #53）。已納入 2026-10-24 核准的決定：#73（單元卡應用層級）、#75（課程配方不記錄客戶）、#80／ADR 0005（逐頁腳本併入簡報）

## 目標

這份規格規定怎麼把維護者整理的知識庫資料夾單向匯入平台的知識庫，也就是 #53 的模組框架、模組卡、單元卡與課程配方。內容包括四件事：

- 每個來源欄位對到哪個實體與欄位，或者為什麼不匯入。
- 資料品質問題怎麼處理。
- 重跑匯入時平台怎麼反應。
- 客戶名稱怎麼處理。

實際匯入要等 schema v2 與登入完成（見 #53 的「不在範圍內」）。這份規格是那張實作票的依據。

文中的統計數字都取自 2026-10-24 的知識庫快照。所有例子都是虛構的。真實的檔名、路徑、客戶名稱和卡片內容不會出現在本 repo。

## 前提與決定

| 決定 | 選擇 | 理由 |
| --- | --- | --- |
| 真相來源 | 現階段以維護者的資料夾為準。平台單向匯入，而且可以重跑 | #53 的 Further Notes。平台的結案與草稿審核做好以前，維護工作留在資料夾 |
| 匯入範圍 | 只匯入知識庫資料夾裡的四類文件：模組框架文件、模組卡、單元卡、課程配方 | 原始課綱暫存區和維護腳本是產生卡片的中間產物，本身不是知識 |
| 不匯入 | 場次資料夾與提案資料夾裡的原檔，例如簡報、課綱、合約 | 檔案不進平台，而且含客戶機密。轉檔另案評估（見「原檔轉檔的接點」） |
| 課程配方的地位 | 匯入成 `CourseRecipe`。不轉成藍圖，也不建立專案、課程或場次 | ADR 0002 的修訂 |
| 目標形狀 | 以 #53 的實體為準。欄位名稱沿用已合併的設計稿（`src/lib/mockup/types.ts`，#55–#61：單元卡、課程配方、標籤、結案草稿）與藍圖 schema（`src/lib/blueprint/schema.ts`，#56）。#73、#75、#80 的決定還沒反映在程式，本規格以決定為準。之後這些定義若有變，要回頭修改本規格 | schema v2 還沒設計。本規格需要、但設計稿還沒有的欄位，列在「對模型的修改建議」 |
| 誰執行 | 由人在本機執行匯入指令（建議 `pnpm kb:import <資料夾> [--apply]`）。指令讀本機資料夾，再寫進 Supabase | 素材不在 repo 裡 |
| 匯入只做機械正規化 | 匯入只做機械處理：佔位字串轉成 null、整理空白、解析表格與年月。歸類、標題、重複這類內容問題只標記，回到資料夾修正。唯一的例外：欄位明顯抽錯時（見 Q10），可以改用來源 id 裡對應的那一段當備用值，但一定要加上旗標 | 資料夾是真相來源。平台自己修正的內容，下次匯入時不是被覆蓋，就是和資料夾分岔 |
| 機密 | 客戶只存在專案上，知識庫的實體（單元卡、課程配方、模組卡）都不記錄客戶，維護者資料裡的配方客戶欄位不匯入（#75）。知識庫的文字欄位都是可重用欄位，不能含客戶名稱；命中名稱的先標記並暫停使用 | ADR 0004、#75。避免 A 客戶的名稱經由知識庫流進 B 客戶的教材 |

## 來源概況

| 文件 | 數量 | 形狀 |
| --- | --- | --- |
| 模組框架文件 | 1 | frontmatter 4 個鍵，內文 7 節（兩層分類一節含 A、B 兩張表） |
| 模組卡 | 9 | 每個模組一張。frontmatter 8 個鍵，內文 5 節 |
| 單元卡 | 276 | frontmatter 7 個鍵（其中 15 張多 1 個鍵），內文 4 節（同樣 15 張多 1 節） |
| 課程配方 | 67 | 29 份有抽出來的單元序列，1 份抽取失敗、單元序列是空的，37 份是 stub |
| 原始課綱暫存區 | 29 份 Markdown | 不匯入 |
| 維護腳本 | 3 支腳本，加一份說明 | 不匯入。只拿來理解欄位是怎麼產生的 |

下面整理維護腳本怎麼運作，用來理解欄位的語意：

- **抽取腳本**讀原始課綱暫存區裡的每一份課綱。它從表格或「標題／NN 分鐘」格式切出單元，再把「模組相同、正規化後標題也相同」的單元合併成一張單元卡。所以同名的單元即使跨課程，也只有一張卡。
  - 模組用關鍵字判定：先看單元標題，再看學習目標，兩者都沒命中，就沿用整門課的模組。
  - 產業由腳本內建的客戶與產業對照表推得，或從場次資料夾名稱推得。
  - 配方的狀態由原檔所在的資料夾推得。
  - 每次重跑都會重寫所有由課綱產生的單元卡與配方，但不會刪除舊檔。
- **歸檔腳本**在一場課結束後整理場次資料夾，把課綱轉成 Markdown，再呼叫抽取腳本。沒有課綱的場次會產生 stub 配方。
- **簡報抽取腳本**依簡報的段落分頁切出單元卡（`extract: deck`）。切出的單元會併入既有的卡，或另建新卡，也會把 stub 配方補成有單元序列的配方。

硬碟上的檔案和腳本的現行版本並不完全一致。例如 stub 配方多了 `audience` 和 `tools` 兩個鍵，也多了「教材模組分佈」一節，但歸檔腳本並不會產生這些內容。另外，模組框架文件寫的 id 規則也和實際檔名不同（見下一節）。**所以匯入程式以實際檔案為準，接受已經觀察到的格式變體，不從腳本或文件推論格式。**

## 欄位對照

每個匯入的實體都有一組共通的匯入追蹤欄位：`id`（平台產生的 UUID）、`origin`（`import` 或 `platform`）、`sourceKey`、`sourceHash`、`revision`、`importedAt`、`retiredAt`、`mergedIntoId`、`importFlags`。用法見「匯入行為」。

### 檔名與 id 規則

| 來源 | 實際格式（例子為虛構） | 文件寫的格式 | 對照 |
| --- | --- | --- | --- |
| 模組卡 | `<模組>_<模組名稱>.md`，frontmatter 的 `id` 是模組代號 | 沒有寫 | 對到 `ModuleCard.moduleId`；檔名不使用 |
| 單元卡 | `<模組>_<單元名稱>.md`，例如 `A4_某雲端工具入門.md`。`id` 等於主檔名；單元名稱去掉標點後截成 30 字，同名碰撞時加 `_<n>` | `<模組>-<課程slug>-<序號>` | 對到 `sourceKey`，不當平台的 id。模組前綴必須等於 `module` |
| 一般配方 | `<YYYYMM>_<客戶>_<課名>` 或 `提案_<客戶>_<課名>`，例如 `提案_某製造業者_AI 入門` | `<年月\|提案>_<客戶>_<課名>` | 對到 `sourceKey`（含客戶段，怎麼存見待決問題）。年月對到 `heldOn`。客戶段不進任何欄位 |
| stub 配方 | 沿用場次資料夾名稱 `<產業>_<YYYYMM>_<客戶>_<主題>` | 同上一列 | 對到 `sourceKey`（同上）。產業前綴對到產業標籤，年月對到 `heldOn` |

現況：

- 單元卡的 id 全部等於檔名，也全部唯一。模組前綴和 `module` 欄位 276 張全部一致。有 5 張的 id 長度剛好到截斷上限，可能被截斷過。目前沒有任何碰撞後綴。
- 配方的 id 有三種前綴：
  - `提案_`：15 份，都是提案。
  - `<YYYYMM>_`：14 份，其中 12 份已交付、2 份籌備中。籌備中配方的年月是預定的月份。
  - `<產業>_`：38 份，包括 37 份 stub，加上 1 份由簡報抽取補成的配方。其中 1 份 stub 的年月段寫的是跨年區間，不是 YYYYMM。
- **兩種 id 都不穩定。**
  - 單元卡的 id 由模組與標題組成，所以改標題或改歸類，id 就跟著換。
  - 配方從提案變成已交付時，前綴會從 `提案_` 變成年月。

  所以平台不拿來源的 id 當主鍵（見「穩定識別」）。配方的 id 含客戶名稱，這和「配方不記錄客戶」衝突，處理方式列在待決問題。

### 模組框架文件 → 模組框架

模組框架在平台上是一份有版本的文件，藍圖對話一律先讀它。它的另一部分規則已經寫成程式常數或純函式（#56、#57、#58）。

匯入時，文件本體整份存成一個新版本。文件裡的表格與規則則拿來**核對**程式常數。兩邊不一致時，匯入報告會標紅，由人決定要改程式還是改文件。

| 來源 | 目標 | 處理 |
| --- | --- | --- |
| frontmatter 的 `id` | — | 不匯入；平台只有一份模組框架 |
| frontmatter 的 `title` | `ModuleFramework.title` | 直接帶入 |
| frontmatter 的 `version`（日期） | `ModuleFramework.sourceVersion` | 直接帶入。平台另外維護一個遞增的 `revision` |
| frontmatter 的 `always_load` | — | 不匯入；「一律先讀」是平台的行為（#53） |
| 「兩層分類」的 A 類表（模組、環境、工具、完整版、精簡版、可達層級） | 核對 `MODULES` 與 `MODULE_IDS`（`src/lib/blueprint/modules.ts`，#79 合併後的單一模組目錄）與模組卡 | 模組代號或名稱和程式不同，是硬錯誤。環境、工具、時數、層級以模組卡為準；和模組卡不一致時標記（現況 0 筆） |
| 「兩層分類」的 B 類表（模組、帶走的產出、完整版、精簡版、方法框架） | 核對 `MODULES`（`src/lib/blueprint/modules.ts`）。「帶走的產出」對到 B 類模組卡的 `scope` | B 類表沒有「可達層級」這一欄 |
| 「判定規則」 | 文件本體 | 藍圖對話與結案草稿（#60）判定模組時依據它。匯入程式的歸類檢查也依據它（見 Q4） |
| 「組裝公式」 | 文件本體。同時核對組課提醒（#58）的常數：B 模組定錨幾個、6H 以下最多幾個 A 模組 | 數字不一致時標記 |
| 「建議規格」 | 核對規格推導函式（#57） | 同上。表中沒列的時數歸到較低的級距，見 Q3 |

| 「5 層應用層級」 | 核對 `APPLICATION_LEVELS` 與 `APPLICATION_LEVEL_LABELS`（`src/lib/blueprint/schema.ts`，現在只有 L1–L5）| 不一致時標記。`na`（不適用，純方法）是 #73 的決定，尚未實作，由 #73 新增；在那之前匯入規則只對到 L1–L5 與 null，#73 完成後改成對到 L1–L5 \| `na` \| null |
| 「檔案與檢索」 | — | 不匯入。這一節描述資料夾的載入方式與檔名慣例，在平台上由篩選與「最相近的 3 份配方」取代（#53） |

## 資料品質規則

每一條規則對應一個 `importFlags` 代碼。標記不會擋下匯入；只有「硬錯誤」會中止整批匯入（見「匯入行為」）。數字都取自 2026-10-24 的快照。

### Q0 已交付的課幾乎都沒有單元序列

- 50 份已交付的配方裡，37 份是 stub，1 份抽取失敗，**只有 12 份有單元序列**。
- 反過來看，276 張單元卡裡有 **158 張只出現在提案或籌備中的配方**，也就是說這些單元沒有實際上過。已交付配方與提案配方之間，沒有共用任何一張單元卡。
- 規則：單元卡加上衍生旗標 `proposalOnly`，每次匯入時依配方狀態重算。知識庫頁和藍圖對話預設照樣列出這些卡，但會標示「僅出現在提案」。要不要預設排除，見待決問題。

### Q1 stub 配方

- **定義**：`extract: stub` 的配方，也就是「單元序列是空的，而且有『主簡報』一節」。現況有 37 份，全部是已交付，`hours` 都是 null，`units` 都是空的。另外有 1 份 `extract: manual` 的配方也沒有單元序列，比照處理，但旗標用 `no_units`。
- **匯入**：建立 `CourseRecipe`，設定 `units: []`、`skeletonOrigin: stub`，並加上旗標 `stub_recipe`。有了 `materialModules`，依模組篩選時也找得到它。
- **使用**：
  - stub 不參與「最相近的 3 份配方」。
  - stub 不能「從配方複製」成新藍圖。
  - stub 不計入單元卡的使用次數。
  - 知識庫頁另外列一份「只有入口，骨架待補」的清單，依簡報數排序。
- **補骨架**：維護者在資料夾用簡報抽取補上單元序列之後，`sourceKey` 不變，下次匯入就當成一般的內容更新：`revision` 加 1，旗標移除。
- 另外有 1 份 stub 的客戶欄位被抽成產業名稱，1 份 stub 的產業欄位和 id 前綴不一致，見 Q10。

### Q2 缺少應用層級

- 276 張單元卡都沒有應用層級。模組框架寫的是「每個單元一個欄位」，但卡片格式沒有這一欄。
- 模組卡只有可達範圍（`levelRange`）。B 類模組的範圍語意不明，例如治理類模組被標成最高的 L5，但它並不是自動化。
- #73 的決定：單元卡與藍圖單元的 `level` 用同一組值，`L1`–`L5`、`na`（不適用，純方法），或 null（未評）。「未評」和「純方法」是兩種狀態。
- **匯入**：沒有來源層級的卡一律設為 null（未評），**不設 `na`**。不從模組範圍自動推定，因為推定值會被當成事實複製進藍圖。只有來源明確寫了純方法，才對到 `na`（現況 0 張）。
- **補齊**：有兩種做法，採哪一種見待決問題。
  - 另跑一次批次：AI 依單元卡內容，在 `levelRange` 範圍內提出建議，再由講師逐張確認。
  - 由維護者在資料夾補上 `level:` 欄位，之後匯入就以來源為準。
- **檢查**：有了 `level` 之後，落在模組 `levelRange` 之外的卡加上旗標 `level_out_of_range`。
- 未評的單元卡複製進藍圖後，藍圖單元也是未評，並出現在準備度裡（#73）。

### Q3 標籤缺漏與不一致

**對象**

- 現況：單元卡沒有這個標籤。配方的 `audience` 是自由文字，67 份中只有 23 份有值，另有 1 份連這個鍵都沒有。有 2 份是課綱的多行條列被串成一行，3 份含客戶名稱。
- 規則：對象標籤用關鍵字推定（原文是否保留見待決問題）：
  - 「主管」「經營」：主管經營層。
  - 「全體」「全員」：全員。
  - 職務名稱：特定職能。
  - 「種子」：種子團隊。

  推不出來就留空，並加上旗標 `audience_untagged`。單元卡不從配方繼承對象標籤。

**工具**

- 現況：單元卡沒有這個標籤。30 份一般配方中，17 份的 `tools` 是空白；有值的也是自由文字，分隔符號不一致，還夾帶方案等級與作業系統。
- 規則：工具字彙以 A 類模組卡的 `tools` 為種子，再加上別名表（同一個工具的不同寫法）。
  - 配方：切開、拿掉括號、對照字彙。對不到的保留原文，並標記 `unknown_tool`。
  - 單元卡：標題出現字彙裡的工具名稱時，推定為工具標籤，並註明「由標題推定」。

**產業**

- 現況：單元卡的 `industries` 是腳本由客戶對照表推得的。34 張有多個值，47 張含「通用」。配方的產業是單值。
- 規則：
  - 單元卡的產業標籤在每次匯入時由配方重算。
  - 配方的產業以單值帶入。
  - 匯入程式在記憶體裡發現同一個客戶在不同配方裡的產業不同時（現況 1 個客戶），只寫進匯入報告，不存進平台。

**應用場景**

- 現況：沒有任何檔案有這個標籤。
- 規則：匯入時留空。字彙還沒定，模組框架只舉了簡報、數據分析、文書、圖片、客服這幾個例子。

**規格**

- 規格不另外存，由時數推得：先用 `declaredHours`；沒有的話，用 `units[].minutes` 加總，但只有每一列都有分鐘數時才算。兩者都沒有就是「未知」，現況有 44 份。
- 落在兩個級距之間的時數歸到較低的那一級（已合併的 #57 實作，#80 寫進 GLOSSARY），所以現有 3 份 26 小時的配方是系列班，10 小時是一日，不需要另外處理。

### Q4 歸類可疑的單元卡

抽取腳本用固定順序的關鍵字判定模組；都沒命中時，就沿用整門課的模組。所以歸錯的卡多半有跡可循。

匯入時用下列啟發式規則標記，但不修改 `module`，修正要回到資料夾做。表中「現況」的數字是用抽取腳本現行的關鍵字表算出來的；匯入程式改用模組框架與模組卡的關鍵字之後，數字會有些出入。

| 旗標 | 判定 | 現況 |
| --- | --- | --- |
| `module_fallback` | 標題與學習目標都沒命中任何模組的關鍵字，也就是模組是從整門課繼承來的。關鍵字取自模組框架的判定規則與模組卡的工具清單 | 105 張（38%），其中 A1 43 張、A4 29 張 |
| `module_tool_conflict` | 標題寫了另一個 A 類模組的工具，卻沒寫自己模組的工具。例如標題是「某雲端工具的串接」，卻歸在 A3 | 15 張 |
| `module_multi_hit` | 標題同時命中兩個以上模組的關鍵字 | 7 張 |
| `b_module_names_tool` | B 類（不綁工具）的卡，標題卻寫了特定工具 | 4 張 |
| `module_stats_mismatch` | 以模組為單位比對：單元卡數量和模組卡「現況」的統計差距過大時，提醒人工檢查。可能是歸類太寬，也可能是統計過時。例如某張模組卡寫只有 3 個場次，但這個模組有 33 張單元卡，出現在 12 份配方裡 | 1 個模組 |

已知的規則漏洞，供維護者修抽取腳本：

- 工具縮寫後面接全形標點時，比對不到。
- 英文的「cloud」不在雲端模組的關鍵字裡。標題寫英文的雲端版名稱時，會先被桌面自動化的關鍵字抓走。
- 同一個產品名稱可能同時屬於對話型（A1）與 Agent（A5）。

### Q5 重複與近似重複的單元卡

抽取腳本只合併「同模組、正規化後標題完全相同」的單元，所以近似重複的卡很多。

| 型態 | 判定 | 現況 |
| --- | --- | --- |
| 同標題跨模組 | 正規化後標題相同，但模組不同 | 1 組：同一個收尾類標題分成 3 張卡 |
| 近似標題 | 正規化後標題相似度 ≥ 0.7，或其中一方的標題包含另一方 | 64 對（同模組 55 對、跨模組 9 對）。相似度 ≥ 0.85 的有 17 對 |
| 同目標、不同標題 | 學習目標相似度 ≥ 0.8 | 8 對，例如一張用比喻式的標題，另一張用平鋪直敘的標題 |

常見的成因：

- 標題多了縮寫括號。
- 標題殘留時段前綴。
- 同一段教學換了產業說法，例如「用試算表整理銀行對帳單」與「用試算表整理工廠出貨單」（虛構的例子）。
- 同一門課的提案版和交付版各抽了一次。

規則：

- 匯入不自動合併。合併會改變配方的單元序列，而資料夾才是真相來源。
- 近似重複的卡成對寫進匯入報告，並加上旗標 `near_duplicate`，由維護者在資料夾合併。合併之後，被刪掉的那張在平台上設定 `mergedIntoId`（見「匯入行為」）。
- 只差在產業說法的近似重複，建議合併成一張單元卡，產業上的差異改由產業素材包處理。

### Q6 used_in／times_used 一致性

- 這兩個欄位不匯入，平台由配方的單元序列推得，匯入時只拿來核對。現況：
  - 每張卡的 `times_used` 都等於 `used_in` 的長度（0 筆不一致）。
  - `used_in` 和配方的 `units` 雙向一致（0 筆不一致）。
  - 每一筆引用都解析得到。
- 不一致時以配方為準，並加上旗標 `derived_field_mismatch`。
- **使用次數被灌水**：37 張 `times_used: 2` 的卡裡，只有 6 張是真正跨課程重用。
  - 28 張來自兩份單元序列相同的提案：一份是通用版，另一份是給特定客戶的版本。
  - 3 張來自同一門課的兩版提案。

  規則：平台顯示「用過的配方」時，單元序列相同的配方，以及帶有 `recipe_version_pair` 旗標的同門課不同版本，都只算一次。使用次數不再當排序依據。
- 抽取腳本重跑時，會重寫由課綱產生的卡，可能蓋掉簡報抽取補上的 `used_in`。核對就是為了抓到這種情況。

### Q7 配方狀態

| 來源的值 | 份數 | 平台的 `status` | 意義與用法 |
| --- | --- | --- | --- |
| 已交付 | 50（其中 stub 37） | `delivered` | 原檔在場次資料夾。填 `heldOn`。挑「最相近的 3 份配方」時優先 |
| 提案 | 15 | `proposal` | 原檔在提案資料夾，但不在以年月開頭的子資料夾裡。可能沒成交，也可能還在談。可以當範例，但要標示「提案」 |
| 籌備中 | 2 | `preparing` | 原檔在提案資料夾底下、以預定年月開頭的子資料夾裡。用法同提案。不填 `heldOn` |

- 狀態是腳本依原檔所在的資料夾推得的，不是人填的。
- 配方的狀態**不對應**平台的專案狀態（洽談中、進行中、封存），也不對應課程的結案。匯入不會建立專案、課程或場次，配方只是知識庫裡的一筆紀錄。
- 名稱相近的配方共有 9 對，其中 3 對是同一門課的不同版本，加上旗標 `recipe_version_pair`，在報告中成對列出：
  - 同一門課的提案版與交付版同時存在：1 對。
  - 同一門課的兩版提案：1 對。
  - 同一門課拆成 Day1、Day2 兩份：1 對。

  另外 6 對是同一個系列活動在不同月份的場次，屬於合理情況，不處理。
- 提案變成已交付時，id 的前綴會跟著變（見「穩定識別」）。

### Q8 時數與分鐘數

- 配方的 `declaredHours` 和單元分鐘數的加總相差超過 30 分鐘時，加上旗標 `hours_mismatch`。現況 7 份，例如宣稱 30 小時，單元卻只加到 16 小時。
- `declaredHours` 是 null，但標題或 id 寫了「<n>H」時，不自動填入，只加上旗標 `hours_in_title`（2 份）。
- 單元卡：
  - 分鐘數是 null 的有 36 張，其中 15 張來自簡報抽取。
  - ≥ 240 分鐘的有 7 張，也就是整天被當成一個單元，加上旗標 `oversized_unit`。
  - ≤ 10 分鐘的有 5 張。
- 同一張單元卡在不同配方裡的分鐘數可能不同（現況 5 張）。配方保留各自的分鐘數，單元卡的 `minutes` 只當參考值。

### Q9 標題雜訊與非教學單元

- 標題殘留時段前綴（上午、下午、第 N 堂、Day N）的有 24 張，含「｜」分隔符號的有 23 張，加上旗標 `session_prefix_in_title`。
- 純後勤或開場收尾的單元（例如休息、開場、收尾、Q&A）有 6 張，標題含這類字樣的有 20 張，加上旗標 `logistics_unit`。這些不是可以重複使用的教學，建議維護者刪除，或併入相鄰的單元。在那之前，它們不列入藍圖對話的單元卡清單。
- 標題 ≤ 4 個字的有 9 張，id 可能被截斷的有 5 張，這兩類只標記。

### Q10 配方欄位抽錯

- 標題抽到課綱的節標題或空字串（3 份）：`bad_title`。
- 客戶欄位被抽成產業名稱（1 份 stub）：客戶欄位不匯入，所以只影響名稱表，匯入報告提醒維護者修正，不加旗標。
- stub 的產業欄位和 id 前綴不一致（1 份，起因是 id 的年月段格式不標準）：`industry_prefix_mismatch`，以 id 前綴為準。
- 對象欄位是多行條列被串在一起（2 份）：`audience_garbled`。
- 有 2 份配方的 id 或標題含外部講師的個人姓名，視同客戶名稱處理（見「機密處理」）。

## 匯入行為

### 流程

1. **讀取**：解析四類文件。接受已知的格式變體；不認得的鍵與節寫進報告，不中止匯入。
2. **驗證**：只要有硬錯誤就中止，不寫入任何資料。現況 0 個硬錯誤。硬錯誤只有以下幾種：
   - frontmatter 無法解析。
   - `module` 不在 A1–B4 之內。
   - 單元卡的 id 不等於檔名，或 id 重複。
   - 單元卡的模組前綴和 `module` 不同。
   - 配方的 `units` 解析不到單元卡。
   - 模組卡的集合和 `MODULES` 不一致（例如維護者新增了預留的 A6，程式還沒跟上）。
   - 找不到模組框架文件。
3. **正規化與標記**：佔位字串轉成 null；解析表格與年月；計算衍生欄位；套用 Q0–Q10 的旗標；掃描客戶名稱。
4. **比對**：以 `sourceKey` 對照平台上既有的 `origin: import` 資料，算出哪些要新增、更新、維持不變、退役，以及哪些疑似改名。
5. **報告**：輸出匯入報告。**預設只產生報告（dry run）**，加上 `--apply` 才寫入，而且在一個交易內寫完。
6. **寫入**：用 service role client，並自己加上工作區條件（ADR 0004）。schema v2 完成前不實作這一步。

匯入報告含真實的客戶名稱與檔名，只能輸出到本機上 repo 以外的路徑，不能貼進 issue、PR 或 commit。匯入程式本身和它的測試放在 repo 裡，測試資料一律虛構。

### 穩定識別

- 平台的主鍵一律是平台產生的 UUID。`UnitSource`、配方的單元序列、模組卡的代表配方，存的都是 UUID。
- `sourceKey` 是來源的主檔名（單元卡、配方），或模組代號（模組卡）。它在 `origin: import` 的資料裡唯一，用來對應下一次匯入的同一筆資料。
- `sourceHash` 是正規化後「來源欄位」的雜湊，用來判斷內容有沒有變。它不包含衍生欄位（`used_in`、`times_used`、`industries`、`modules`），也不包含路徑類的欄位。
- **長期解法**：請維護者在每張卡與每份配方的 frontmatter 加一個永遠不變的 `uid`。有了 `uid` 就用它當 `sourceKey`，改名、改歸類都不必再用猜的（見待決問題）。

### 重跑與變更

| 來源的變化 | 怎麼判定 | 平台的動作 |
| --- | --- | --- |
| 新檔案 | `sourceKey` 不存在 | 建立新資料，`revision` 為 1 |
| 沒變 | `sourceHash` 相同 | 不動資料；衍生欄位照常重算 |
| 內容改了 | `sourceHash` 不同 | 覆寫來源欄位，`revision` 加 1，平台欄位保留 |
| 檔案不見了 | 這次匯入沒有這個 `sourceKey` | 設定 `retiredAt`，不刪除資料，所以已經複製進藍圖的單元仍然顯示得出來源。退役的卡不會出現在篩選結果與藍圖對話裡 |
| 消失後又出現 | 同一個 `sourceKey` 回來了 | 清除 `retiredAt`，當成內容更新處理 |
| 改歸類 | 舊 key 消失、新 key 出現，兩者只差在模組前綴，而且「用過它的配方」相同 | 自動視為同一張卡：更新 `sourceKey` 與 `moduleId`，保留 UUID |
| 改標題，或疑似改名 | 舊 key 消失、新 key 出現，兩者同一個模組、「用過它的配方」相同，而且標題相似度 ≥ 0.85 或學習目標相似度 ≥ 0.9 | 不自動處理，先列在報告。用 `--rename 舊=新` 確認後保留 UUID；沒確認的話，當成「退役一張、新增一張」 |
| 合併重複的卡 | 舊 key 消失，而且它原本在配方裡的位置全部改成某一張既有的卡 | 舊卡設定 `retiredAt` 與 `mergedIntoId` |
| 配方從提案變成已交付 | 提案配方消失，同時出現一份標題相近的已交付配方（配方不記錄客戶，不用客戶比對） | 列在報告等待確認。確認後保留 UUID，並更新 `status` 與 `heldOn`。兩份同時存在時不處理（見 Q7） |
| stub 補上了單元序列 | 同一個 `sourceKey`，`units` 從空的變成有內容 | 當成一般的內容更新，並移除 `stub_recipe` 旗標 |
| 模組框架或模組卡改了 | `sourceHash` 不同 | 模組框架存成新版本。模組卡加一個 `ModuleCardVersion`，`note` 寫「知識庫重新匯入」 |

### 欄位歸屬

- **來源欄位**由匯入擁有，也就是上面對照表中帶入的欄位。現階段這些欄位在平台上唯讀，要修改就改資料夾。
- **平台欄位**由平台擁有，包括應用層級、講師在平台上加的對象／工具／應用場景標籤、機密審核的結果、近似重複的處理紀錄。匯入永遠不覆寫平台欄位。
- 如果來源日後新增某個欄位（例如維護者開始填 `level:`）：來源有值時就寫入，這個欄位從此變成來源欄位；來源是 null 時，不清掉平台上已經有的值。
- `origin: platform` 的資料，也就是 #60 結案草稿審核後收進知識庫的單元卡與配方，匯入一律不碰。它們和匯入資料的標題相近時，只標記 `near_duplicate`，不自動合併。
- 等後端的結案與草稿審核上線後，再一次性切換：停止匯入，把 `origin: import` 的資料轉成由平台維護。這件事另外開票。

### 和 `UnitSource` 的關係

- 新藍圖的單元從單元卡複製出來時，`source` 寫成 `{ kind: "unit_card", id: <單元卡的 UUID>, version: null, unit: <單元卡當時的標題> }`。`version` 照 #56 已合併的定義填 null（單元卡不分版本）。`id` 絕對不用 `sourceKey`，因為它會變。
- 同時複製 `title`、`minutes`、`objective`、`method`、`outcome`、`module`、`level`。`level` 照原值帶入（#73）：單元卡是未評（null），藍圖單元也是未評，並出現在準備度裡；`na` 帶入 `na`。另外：
  - 單元卡的 `objective`、`method` 或 `outcome` 是 null（原本是佔位字串）時，藍圖的 `Unit` 這幾格是必填的，要由藍圖對話補齊，而且 `reuse` 不能是「沿用」。
- 從配方複製時，照配方的單元序列逐一複製。每個單元的 `minutes` 用配方那一列的分鐘數，那一列是 null 才用單元卡的參考值。stub 配方不能複製。
- 單元卡之後因為重新匯入而改版、退役或合併，已經存在的藍圖都不受影響（ADR 0002）。UI 可以依 `retiredAt` 或 `mergedIntoId` 顯示「已退役」或「已合併至某張卡」。如果之後想顯示「單元卡已更新」，`version` 要改填單元卡的 `revision`，見待決問題。
- 單元卡頁上有兩種使用紀錄，分開顯示：
  - 「被哪些課程配方用過」：由匯入的配方推得。
  - 「平台上哪些課程用過它」：由藍圖單元的 `source.id` 推得。

- 單元卡的標題可能含客戶的專案或產品名稱。這不是公司名稱，所以從配方的客戶欄位建立的名稱表抓不到。

### 規則

1. **知識庫沒有客戶綁定欄位。** 單元卡、課程配方、模組卡與模組框架的文字欄位，包括配方的 `title`、`audience`，一律是可重用欄位，不可以含客戶名稱。`sourceKey` 是追蹤用的鍵，不是內容，但配方的 id 含客戶段，怎麼存見待決問題。
2. **名稱表在匯入時建立，只放在記憶體，不進 repo，也不存進平台。**
   - 來源：配方的 `client` 欄位、一般配方 id 與 stub id 裡的客戶段（現況 44 個名稱，不含團隊自己的品牌），再加上維護者提供的別名表。別名表包含簡稱、英文名稱、客戶的產品或專案名稱、外部講師的姓名；它放在資料夾裡，不放在 repo。
   - 2 個字以下的名稱（現況 6 個）只比對完整的詞，並讓維護者列出例外，避免誤判。
3. **可重用欄位命中名稱時，加上旗標 `client_name_in_reusable_text`。** 這筆資料照常匯入，知識庫頁也看得到，但在講師處理之前，不送進藍圖對話，也不參與「最相近的 3 份配方」。處理方式有兩種：
   - 在資料夾裡改寫（優先）。
   - 在平台上標記「已確認無礙」。這是平台欄位，重新匯入時會保留；但內容雜湊改變後要重新檢查。
4. **送進藍圖對話的內容只來自通過檢查的欄位。** 因為配方不記錄客戶，不再有「同一個客戶自己的專案可以原樣帶入」的例外，也不再有「送進去前把客戶欄位改成產業代稱」的步驟。
5. **結案草稿用同一份名稱表。** #60 審核結案草稿時，講師會排除機密內容。草稿也用同一份名稱表預先標出可疑的字句，讓兩邊規則一致。草稿的配方名稱由內容組成（比照 #75 的中性名稱），不沿用課程名稱。

| --- | --- | --- | --- |

## 原檔轉檔的接點

這一節不在本規格範圍內。pdf、Word、簡報等原檔轉成 Markdown 的工具（例如 markitdown）另案評估。

本匯入程式**不**轉檔，只讀已經是 Markdown 的知識庫文件。轉檔會接在三個地方：

1. **資料夾端，匯入的上游。** 維護者的歸檔腳本已經用轉檔工具把課綱 docx 轉成原始課綱，再抽成單元卡與配方。換工具或改善轉檔品質，影響的是卡片內容，匯入規則不變。
2. **補 stub 的單元序列。** 37 份 stub 中有 22 份附了簡報。用簡報抽取補單元序列時，要先把簡報轉成文字。這是改善 Q0、Q1 的主要途徑，在資料夾端做。
3. **平台的結案（#60）。** 講師上傳最終版簡報之後（講稿在簡報的 speaker notes，不再有獨立的逐頁腳本，見 `docs/adr/0005-page-script-merged-into-slides.md`），要轉成文字，交給 AI 拆成草稿。這屬於結案草稿的票，不屬於匯入。
